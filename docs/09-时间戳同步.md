# 09 时间戳同步

本章说明 P1 数据里各个时间戳的含义，怎样用它们把左右手、手套与 Tracker 对齐，
平时看哪些指标判断时间同步是否正常，以及出现时间相关的提示、异常与错误时该怎么处理。
各字段与接口的完整定义见《RevoHuman SDK 参考手册》第 6.1、6.2、6.6 节。

## 1. 先记住三条

1. **对齐一律用采样刻 `sample_wall_ns`**。下面这些都是**到达时刻**，不要用来对齐：
   帧里的 `recv_wall_ns`、MCAP 消息自带的 `log_time`、rosbag 里每条消息自带的时间、`revohuman-live` 广播的时间。
   手套数据到达主机比采样晚约 10 ms，Tracker 晚不到 1 ms；用到达时刻对齐，手套相对 Tracker 会错开约 10 ms。
2. **拿到的帧都在精度要求之内**。时间戳达不到精度要求的帧 SDK 不派发，配对精度达不到要求的双手对子不输出。
   帧上没有「这一帧准不准」的字段，不需要逐帧检查；代价是出问题的那段时间没有数据（第 4 节）。
3. **同一个程序里，所有 `*_wall_ns` 共用同一个时间基准**，跨手、跨设备可以直接相减。
   多台主机之间能否对齐取决于主机对时（第 7 节）。

## 2. 时间戳从哪里来

所有 `*_wall_ns` 都是 Unix 时间（UTC）的纳秒数，与 Python 的 `time.time_ns()` 同一个时钟，
转成可读时间用 `datetime.datetime.fromtimestamp(ns / 1e9)`。

手套和 Tracker 各自带一个设备内部计数（手套 1 ms 一格，Tracker 48 MHz），每一帧都记下采样那一刻的计数值。
SDK 在主机上持续测量设备计数与主机时钟的对应关系，把计数换算成主机时间，得到 `sample_wall_ns`。
这个换算建立在主机的硬件时钟上，NTP 平滑调整主机时钟的快慢（调频）不影响它；主机时钟跳变的影响见第 7 节。

| 数据 | 采样刻 | 到达刻 | 设备原始计数 | 说明 |
|---|---|---|---|---|
| 手套 `GloveFrame` | `sample_wall_ns`：编码器采样的时刻 | `recv_wall_ns`，约晚 10 ms | `device_tick`（1 ms 一格） | 采样刻精度在 0.2 ms 以内 |
| 双手 `PairedFrame` | `left.sample_wall_ns` / `right.sample_wall_ns` | 各自的 `recv_wall_ns` | — | `skew_ns` = 右 − 左；双手硬件同步时恒为 0 |
| Tracker `TrackerFrame` | `sample_wall_ns` | `recv_wall_ns`，晚不到 1 ms | `timecode`（约 89.5 秒回绕一次）/ `tc_unwrapped`（展开值，跨帧比较用它） | 含一个固定偏置，见 3.3；被遮挡时 `pose` 为 `None`，时间戳照常有 |
| 两只 Tracker `PairedTrackerFrame` | `left` / `right` 各自的 `sample_wall_ns` | — | — | 两只 Tracker 各自采样，`skew_ns` 不为 0，最多约 ±2 ms |
| 手套按键 `ButtonEvent` | `sample_wall_ns`：第一次看到这次按下的那一帧手套数据的采样刻 | `recv_wall_ns` | — | 时间基准还没建立时为 `None`，此时用 `recv_wall_ns` |

带触觉或腕部相机的型号，触觉与相机各有自己的采样刻，见参考手册第 6.1 节。

## 3. 怎样对齐

### 3.1 左右手：直接用配对帧

`kit.synchronizer().subscribe()`（录制文件里的 `/paired` 话题）输出的每一对 `PairedFrame` 已经是同一时刻的左右手。
P1 用 `open_kit()` 打开时默认建立双手硬件同步：两只手在同一时刻采样，`skew_ns` 恒为 0，不需要再做任何对齐。

- 配对精度默认要求 1.0 ms（`pair_accuracy_ms=1.0`）。硬件同步没建立或中途丢失时，SDK 改用两只手各自的采样刻配对，
  这时 `skew_ns` 不为 0，但仍在 1.0 ms 的要求之内；达不到要求的对子不输出。
- 只接受硬件同步的对子时，第一次取配对器时传入 `kit.synchronizer(pair_accuracy_ms=0.0)`。
  同一个 `kit` 只建一个配对器，之后再传参数不起作用，所以要在调用 `kit.recorder()` 等其他接口之前先取一次。
- 录制文件的元数据 `revohuman.sync_health` → `sync_strict` 记录这一段双手是否全程硬件同步（《04-数据录制》第 3 节）。

### 3.2 手套与 Tracker：按采样刻就近匹配

手套 200 Hz、Tracker 约 250 Hz，两边不在同一时刻采样，要按 `sample_wall_ns` 找最近的一帧（或在两帧之间插值）。
下面的函数对每个手套时刻找采样刻最近的 Tracker 帧，差距超过 `max_gap_ns` 的记为 `-1`（Tracker 被遮挡、断流时会出现）：

```python
import numpy as np


def nearest(t_query, t_ref, max_gap_ns=10_000_000):
    """对 t_query 的每个时刻，在 t_ref（升序，至少 2 个）里找采样刻最近的下标；差距超过 max_gap_ns 记为 -1。"""
    t_query = np.asarray(t_query, dtype=np.int64)
    t_ref = np.asarray(t_ref, dtype=np.int64)
    i = np.clip(np.searchsorted(t_ref, t_query), 1, len(t_ref) - 1)
    i = np.where(t_query - t_ref[i - 1] <= t_ref[i] - t_query, i - 1, i)
    return np.where(np.abs(t_ref[i] - t_query) <= max_gap_ns, i, -1)
```

用法（`paired` 是双手配对帧的列表，`tracker_right` 是右手 Tracker 帧的列表，来自录制文件读回或在线订阅）：

```python
trk = [f for f in tracker_right if f.pose is not None]          # 去掉被遮挡、没有位姿的帧
idx = nearest([pf.right.sample_wall_ns for pf in paired], [f.sample_wall_ns for f in trk])
for pf, k in zip(paired, idx):
    if k >= 0:
        joints, pose = pf.right.joints_deg, trk[k].pose            # 同一时刻的右手关节角与右手位姿
```

Tracker 约 4 ms 一帧，就近匹配带来的时间误差最多约 2 ms。需要更细时，位置用两帧之间线性插值，姿态用球面插值（slerp）。

### 3.3 Tracker 的固定偏置

Tracker 的 `sample_wall_ns` 里包含一段设备内部的固定延迟，SDK 默认不扣除，所以 Tracker 相对手套有一个**固定的**偏置。
它在同一只 Tracker 上前后一致，不影响 Tracker 自身的时序（速度、加速度、前后帧间隔），
只在做手套与 Tracker 之间毫秒级以内的绝对对齐时才需要处理。扣除方法见参考手册第 6.1 节「绝对相位」。

### 3.4 ROS 2 与 rosbag

ROS 2 节点发布的所有 `header.stamp` 都是采样刻，双手的 `joint_states` 取左手的采样刻（双手硬件同步时两手相同）。
rosbag 给每条消息记的时间是到达时刻，跨话题对齐时用消息里的 `header.stamp`（《06-ROS2》第 6 节）。

### 3.5 实时广播 revohuman-live

`revohuman-live` 的广播只用于实时显示：里面的时间是主机收到数据的时刻，
而且时间戳门关着时它照常广播（第 4 节）。需要对齐的数据，请录制（《04-数据录制》）或在自己的程序里订阅（《04-数据录制》第 9 节）。

## 4. 时间戳门

每只手套有一道**时间戳门**（日志里叫「录制门」）：SDK 确认这只手套的采样刻可信时门开，帧正常派发；
不可信时门关，这段时间的帧不派发给订阅方，只计数。门关的原因消失后自动重开，不需要重连。

**刚打开手套时**，SDK 要先建立时间基准，门会关一小会儿，日志里依次出现 N2104（`untrusted`，级别 INFO）、N2105、N2101，这是正常的。
所以打开后的前几十毫秒读不到数据，`recv(timeout=...)` 要给够时间。

**运行中门关**时：

- 订阅方这段时间收不到该手的帧，双手配对帧也停止输出；日志出现 N2102（附原因），重开时出现 N2103（附关了多久、拦下了多少帧）。
- 正在录制时，用 `kit.recorder()` 建的录制器会把当前这一段整段作废（N2501，《04-数据录制》第 5 节），门重开后下一段可以照常录。
- 门关着时调用 `rec.start()` 抛 `CaptureGateClosed`（错误码 1600）。

读取门的状态：

| 读法 | 含义 |
|---|---|
| `glove.capture_ok` | 门是否开着（`kit.glove("left")` 得到 `glove`） |
| `glove.capture_cause` | 门关的原因大类（第 6.2 节），门开时为 `None` |
| `glove.stamp_trust` | 时间戳可信度：`trusted` 正常；`coasting` 精度略降但仍在要求之内，门保持开着，照常出数据；`untrusted` 不可信，门随之关闭 |
| `glove.on_capture_gate = callback` | 门每次开或关时调用 `callback(glove, ok, detail)`，`detail["cause"]` 是原因大类；回调在 SDK 的线程里执行，不要在里面做耗时操作 |
| `kit.status()["gloves"]["left"]` | 其中的 `capture_ok`、`stamp_trust` 同上 |

`glove.subscribe(gated=False)` 得到的订阅在门关时也照常收到帧，这些帧的 `gate_open` 为 `False`，
它们的 `sample_wall_ns` 不可信，只能用于显示或排查，不要用于分析和对齐。

Tracker 没有这道门：Tracker 在时间换算建立之前的帧不派发（只在启动后的最初片刻），之后一直派发。
Tracker 的数据可不可用由基站几何检查把关（《03-基站使用与配对》第 7 节）。

## 5. 查看同步状态

下面的程序打开整套设备，采 10 秒后打印时间同步的各项指标（运行时手套与 Tracker 不能被其他程序占用）：

```python
import time
from revohuman import open_kit

with open_kit("P1") as kit:
    sync = kit.synchronizer()
    time.sleep(10)
    for hand in ("left", "right"):
        g = kit.glove(hand)
        st = g.stats()
        gate = st.stream["capture_gate"]
        print(hand, "门开:", g.capture_ok, "可信度:", g.stamp_trust, "采样率:", st.effective_rate_hz,
              "被拦帧:", st.stream["frames_blocked"], "门开关记录:", len(gate["transitions"]))
        print("   采样刻档位:", st.stream["frames_by_tier"])
        lat = st.latency
        print("   链路延迟 ms p05/p50/p95:", lat["p05_ms"], lat["p50_ms"], lat["p95_ms"],
              "告警:", lat["high_alarm"], lat["jump_alarm"])
    s = sync.stats()
    print("配对档位:", s["pairs_by_tier"], "被拦对子:", s["pairs_blocked"], s["pair_block_reason"])
    print("硬件同步:", kit.pair.synchronized, "丢失:", s["strict_sync_lost"], "重建次数:", s["resyncs"])
    for role, r in kit.status()["tracker"]["roles"].items():
        print("tracker", role, "在线:", r["online"], "最新位姿距今 s:", r["pose_age_s"])
```

各项指标的正常值：

| 指标 | 读取位置 | 正常 | 不正常时说明什么 |
|---|---|---|---|
| 时间戳门 | `glove.capture_ok` | `True` | 门关，这只手不出数据，原因看 `glove.capture_cause`（第 4 节） |
| 可信度 | `glove.stamp_trust` | `trusted` | `coasting` 照常出数据；持续 `untrusted` 按第 6.2 节的原因处理 |
| 采样率 | `stats().effective_rate_hz` | 200 | 明显偏低时检查 USB 线缆、HUB 与主机负载 |
| 被拦帧 | `stats().stream["frames_blocked"]` | 0 | 门关期间没有派发的帧总数 |
| 门开关记录 | `stats().stream["capture_gate"]["transitions"]` | 只有启动时门开的 1 条 | 最近 64 次门开关，每条带 `ok`（开还是关）、`cause`、`wall_ns`（发生时刻）；门重开的那条另带 `closed_ms`（关了多久）与 `blocked`（期间拦下的帧数） |
| 采样刻档位 | `stats().stream["frames_by_tier"]` | 全部在 `sample` | 按采样刻的来源给帧计数：`sample` 为设备计数换算的采样刻；`sample_biased` 含一个没扣除的固定偏置；`recv` 没有换算，等于到达时刻 |
| 链路延迟 | `stats().latency` | `p50_ms` 约 10 | 到达时刻减采样刻的分位数（毫秒）。`high_alarm`：中位数超过 25 ms；`jump_alarm`：中位数比启动时跳变超过 5 ms（一个采样周期）。各触发一次 N2107 |
| 配对档位 | `sync.stats()["pairs_by_tier"]` | 全部在 `hw_sync` | 出现 `independent` 表示有一段是按各自采样刻配对的（硬件同步没建立或丢失），`skew_ns` 不为 0 |
| 被拦对子 | `sync.stats()["pairs_blocked"]` / `["pair_block_reason"]` | 0 / `None` | 达不到配对精度要求而没有输出的对子数与最近一次原因 |
| 硬件同步 | `kit.pair.synchronized`；`sync.stats()["strict_sync_lost"]`、`["resyncs"]` | `True`；`False`、0 | 同步丢失后 SDK 在后台自动重建，重建次数计入 `resyncs`（第 6.1 节 N2202–N2204） |
| Tracker 位姿 | `kit.status()["tracker"]["roles"][手]["pose_age_s"]`，或 `kit.tracker.latest(手)` 返回的第二项 | 小于 0.1 秒 | 越来越大表示这只 Tracker 被遮挡或断流 |
| 录制文件 | 元数据 `revohuman.sync_health` | `sync_strict` 为真，`aborted` 为假 | 这一段没有全程硬件同步 / 这一段作废（《04-数据录制》第 3、5 节） |

ROS 2 节点把手套的 `capture_gate`、`frames_by_tier`、`mapper_quality.stamp_trust` 等字段放在状态话题里，见《06-ROS2》第 3 节。

## 6. 异常与错误

### 6.1 运行期提示

时间同步相关的情况以 N 码日志报告（格式与其余提示码见《07-日志与错误码》第 3 节）：

| 码 | 现象 | SDK 自动做什么 | 你要做什么 |
|---|---|---|---|
| N2101 | 时间戳门已开，开始出帧 | — | 无 |
| N2102 | 时间戳门关（附原因） | 停止派发这只手的帧，原因消失后自动重开 | 按原因处理（6.2）；录制中这一段会作废 |
| N2103 | 时间戳门重开（附关了多久、拦下多少帧） | 恢复派发 | 无；频繁出现时按原因排查 |
| N2104 / N2105 | 时间戳可信度降级（附原因）/ 恢复 | 降为 `coasting` 时照常出帧，降为 `untrusted` 时关门 | 刚打开手套时出现一次 `untrusted`（INFO）是正常的；运行中反复出现按原因排查 |
| N2106 | 时间基准建立未完成，正在重试 | 自动重试 | 长时间不结束时检查 USB 连接与手套固件 |
| N2107 | 手套到主机的传输延迟异常 | 只报告，不影响出帧（采样刻不受传输延迟影响） | 检查 USB 线缆、HUB 与主机负载 |
| N2201 | 双手硬件同步未建立，改用软件配对 | 按各自采样刻配对，`skew_ns` 不为 0 | 要求硬件同步时重新打开设备；见 3.1 |
| N2202 | 双手硬件同步丢失（附哪只手） | 后台自动重建 | 频繁出现时检查 USB 供电与线缆 |
| N2203 | 双手硬件同步已重建 | 恢复硬件同步配对 | 无 |
| N2204 | 双手硬件同步重建失败 | 继续软件配对 | 重新打开设备；仍失败时插拔手套 USB |
| N2205 / N2206 | 双手的采样刻之间出现偏差 / 已恢复 | 只报告，配对照常输出 | 这期间不要把左右手各自的 `sample_wall_ns` 直接相减，以配对帧为准；持续出现时重新打开设备，重建双手同步 |
| N2301 | USB 链路不稳，时间戳暂不可信 | 关门，稳定后自动恢复 | 检查线缆、HUB 与供电 |
| N2302 / N2303 / N2304 | USB 链路复位中 / 恢复失败 / 已恢复 | 自动复位链路 | 恢复失败时插拔手套 USB |
| N2501 | 整条录制作废（附原因与文件路径） | 当前段写完文件、标为作废 | 这一段数据不要用；原因消失后继续录下一段 |
| N2502 | 录制因双手严格同步丢失而中止 | 录制器停止并拒绝再开始 | 重新打开设备，重建双手同步后再录（见 6.3 的 1700） |

### 6.2 时间戳门关的原因

`glove.capture_cause`、N2102 / N2104 日志和门开关记录里的 `cause` 取下面五个值之一：

| 原因 | 含义 | 处置 |
|---|---|---|
| `clock_not_ready` | 时间基准还没建立或已过期，正在重建 | 通常几秒内自动恢复，不用操作 |
| `clock_degraded` | 时间基准质量下降 | 持续出现时检查 USB 线缆、HUB 与主机负载 |
| `host_clock_event` | 主机时钟跳变（休眠唤醒、手动改时间、NTP 步进） | 自动恢复；录制中应避免，见第 7 节 |
| `device_reset` | 手套复位 | 自动恢复；频繁出现时检查供电 |
| `link_unstable` | USB 链路不稳 | 检查线缆、HUB 与供电 |

### 6.3 错误码

| 码 | 异常 | 什么时候出现 | 处置 |
|---:|---|---|---|
| 1600 | `CaptureGateClosed` | 时间戳门关着时调用 `rec.start()` | 等门开（`glove.capture_ok` 为真，或日志出现 N2101 / N2103）后再开始 |
| 1700 | `StrictSyncLost` | 双手硬件同步丢失、录制器已中止（N2502）后又调用 `rec.start()`。只在自己用 `sync.on_sync_lost(rec.abort)` 把两者接起来时出现；`kit.recorder()` 默认不接，同步丢失期间照常录，这一段的 `sync_strict` 记为假 | 重新打开设备（`open_kit()`），重建双手同步后再录 |
| 1205 | `FirmwareIncompatible` | 手套固件不支持或不兼容时间同步功能：这只手套的数据流关闭且不再重连，日志出现 N2405。具体原因是 1203 / 1204（`TimeProbeUnsupported` / `TimeProbeIncompatible`） | 升级手套固件（参考手册第 2.4 节） |

精度要求设得比设备能做到的还严时（如 Tracker 的 `stamp_accuracy_ms` 小于 0.2），创建时直接抛 `ValueError`，不会等到运行中才发现。
错误码的通用用法见《07-日志与错误码》第 4 节。

## 7. 主机时钟与多台主机

- **调频不影响**：NTP 客户端平滑调整主机时钟快慢时，采样刻不受影响，不需要关掉对时。
- **跳变会短暂停顿**：主机时钟跳变（NTP 首次对时或运行中步进、手动改时间、休眠唤醒）时，
  所有 `*_wall_ns` 一起平移同一个量，彼此仍可比较；手套的时间戳门短暂关闭（原因 `host_clock_event`），自动重开。
  录制中遇到会作废当前这一段，所以**录制期间不要改系统时间、不要让主机休眠**。
  只开 Tracker、不开手套时不会做这个平移：各路数据之间仍然一致，但与跳变后的主机时间差一个跳变量。
- **推荐的对时设置**：只在开机时步进、运行中只调频。以 chrony 为例，在 `/etc/chrony/chrony.conf` 里写 `makestep 1 3`
  （开机后的前 3 次对时，偏差超过 1 秒时允许步进，之后只调频），然后查看对时状态：

```bash
chronyc tracking
```

- **多台主机的数据要对齐时**，让它们对同一台 NTP 服务器对时。两台主机之间的对齐精度就是它们之间的对时精度，
  SDK 不检查、也不补偿主机之间的时间差。
- 同一台主机上的多个程序（例如一个程序录手套、另一个程序录别的传感器）用的是同一个主机时钟，`*_wall_ns` 可以直接比较；
  前提是两个程序启动之后主机时钟没有跳变过（跳变的影响见上面第二条）。

## 8. 常见问题

**`recv_wall_ns` 比 `sample_wall_ns` 晚 10 ms 左右，正常吗？**
正常。这是手套到主机的传输延迟，采样刻已经把它扣掉了。延迟大幅变化时 SDK 报 N2107。

**刚打开手套时日志里有 `untrusted（时间基准未就绪）`？**
正常，每只手出现一次，随后 N2105、N2101 表示已就绪。

**录制的一段被标为作废，原因里写着时间戳门关闭？**
这段时间的采样刻不可信，数据不要使用。看 N2102 的原因（6.2）排查；门重开后可以继续录下一段。

**`/paired` 的 `skew_ns` 不为 0？**
硬件同步没建立或中途丢失，SDK 改用了软件配对，对子仍在配对精度要求之内。看日志里的 N2201 / N2202，
只要硬件同步的对子时按 3.1 设 `pair_accuracy_ms=0.0`。

**手套和 Tracker 之间差一个固定的量？**
这是 Tracker 的固定偏置，见 3.3。它不随时间变化；不需要毫秒级以内的绝对对齐时可以不管它。

**数据里的时间是本地时间还是 UTC？**
UTC 的 Unix 时间（纳秒）。显示成本地时间用 `datetime.datetime.fromtimestamp(ns / 1e9)`，它会按主机时区换算。
