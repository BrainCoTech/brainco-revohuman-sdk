# 06 ROS 2

English | [简体中文](zh-CN/06-ROS2.md)

RevoHuman provides three ROS 2 Humble packages, which were built into `~/ros2_ws` in section 8 of *01 Installation and System Requirements*:

| Package | Contents |
|---|---|
| `revohuman_bringup` | launch files and default parameters |
| `revohuman_ros` | nodes: `bimanual_node` (both hands), `glove_node` (single hand) |
| `revohuman_msgs` | custom messages and services |

The nodes publish the glove joint angles and Tracker poses as ROS topics. A P1 glove has 21 joints per hand, plus one Tracker;
P1 has no tactile sensing and no wrist camera, so the corresponding topics do not appear. The one exception is the tactile tare state topic `tactile_tare_state`:
it appears as usual, with `available` set to `false`. For the additional topics of PTV1, see section 7.3 of the *RevoHuman SDK Reference Manual*.

## 1. Before you start

- All software is installed as described in *01 Installation and System Requirements*, both gloves are connected as described in *02 Hardware Connection*,
  and the base station allowlist and base station calibration are done as described in *03 Base Stations and Pairing*.
- **Only one program can open the gloves and Trackers at a time.** While the ROS node is running, do not also run `revohuman-live`,
  the recording scripts of *04 Recording*, or any other program that reads the gloves; the same applies the other way round.
- Every new terminal loads ROS and the workspace automatically (chapter 01 wrote this into `~/.bashrc`), so the commands below use `ros2` directly.

## 2. Starting the node (terminal 1)

Put on both gloves or set them down steadily, then start the bimanual node in terminal 1:

```bash
ros2 launch revohuman_bringup revohuman.launch.py
```

Startup usually takes only a few seconds; the Trackers first need to receive base station signals, so it can take up to about 20 seconds. The node is ready when the following three lines have appeared in the terminal in order (with other log lines in between)
and the last one is `基站几何门：正常` (base station geometry gate: OK):

```text
[bimanual_node-1] [INFO] [1790552908.255867235] [revohuman.pair.bimanual_node]: left=/dev/ttyACM0 right=/dev/ttyACM1 触觉型号=none/none tactile_topics=off pair_mode=strict synchronized=True pair_accuracy_ms=0.0 calibration_srv=off button=off split_tactile=on
[bimanual_node-1] [INFO] [1790552910.049848790] [revohuman.pair.bimanual_node]: tracker left=LHR-XXXXXXXX right=LHR-XXXXXXXX lighthouses=['xxxxxxxx'] frame_id=world
[bimanual_node-1] [INFO] [1790552911.050623370] [revohuman.pair.bimanual_node]: 基站几何门：正常
```

`synchronized=True` in the first line means the sampling of the two gloves is hardware-synchronized; the second line lists the serial numbers of the two Trackers and the declared base stations.

Keep terminal 1 running; all of the following commands are run in **terminal 2**. To stop the node, press `Ctrl+C` in terminal 1.

## 3. Viewing the data (terminal 2)

### 3.1 Topic list

```bash
ros2 topic list | grep revohuman
```

In bimanual mode it should list:

```text
/revohuman/pair/joint_states
/revohuman/pair/status
/revohuman/pair/tactile_tare_state
/revohuman/pair/tracker_delta_left
/revohuman/pair/tracker_delta_right
/revohuman/pair/tracker_pose_left
/revohuman/pair/tracker_pose_right
/revohuman/pair/tracker_status
```

`tracker_delta_left|right` is listed even when no zero pose has been recorded yet, but carries no data; see section 4.

### 3.2 Rates

Joint angles (press `Ctrl+C` to stop):

```bash
ros2 topic hz /revohuman/pair/joint_states
```

Tracker pose:

```bash
ros2 topic hz /revohuman/pair/tracker_pose_left
```

The output of the two commands ends roughly as follows, respectively:

```text
average rate: 199.998
	min: 0.000s max: 0.015s std dev: 0.00051s window: 2205
```

```text
average rate: 249.840
	min: 0.002s max: 0.008s std dev: 0.00037s window: 2757
```

Pass criteria: joint angles at about **200 Hz**, Tracker pose at about **250 Hz** (measured 249.5–249.9). If a rate is clearly lower, first confirm that no other program is reading the gloves,
then check the status in section 3.5. `ros2 topic hz` itself uses CPU, so when the host is very busy the numbers it reports are lower than the actual rate.

ros2 topic echo --once /revohuman/pair/joint_states

### 3.4 Tracker pose

```bash
ros2 topic echo --once /revohuman/pair/tracker_pose_left
```

Example output:

```text
header:
  stamp:
    sec: 1790552972
    nanosec: 990653991
  frame_id: world
pose:
  position:
    x: 0.009542217638544839
    y: -0.011296252865045958
    z: 0.0040065935434237965
  orientation:
    x: 0.21913929068019417
    y: 0.9378284251022679
    z: 0.21161747109497214
    w: -0.1663546280623118
---
```

`tracker_pose_left|right` is the Tracker's absolute pose in the base station frame (defined in section 5.3 of *03 Base Stations and Pairing*),
with `frame_id` `world` (parameter `tracker_frame_id`). Position is in meters, the orientation quaternion follows the ROS convention (x, y, z, w),
and `header.stamp` is likewise the sampling time. These are the raw poses, without the SDK's occlusion-recovery smoothing.
The node does not publish tf: `world` and `revohuman_<hand>_tracker_zero` are only names in the header; to attach them to a tf tree, you need to broadcast the transforms yourself.

### 3.5 Status

The status topics publish one JSON message per second. Their QoS is **RELIABLE + TRANSIENT_LOCAL**, which must be specified when subscribing; otherwise you receive nothing at all:

```bash
ros2 topic echo --once --qos-reliability reliable --qos-durability transient_local --field data /revohuman/pair/status
ros2 topic echo --once --qos-reliability reliable --qos-durability transient_local --field data /revohuman/pair/tracker_status
```

Each command prints one very long line of JSON. For day-to-day use, you only need to look at the following fields (the values in parentheses were measured in a normal run):

`/revohuman/pair/status` (gloves):

| Field | Meaning |
|---|---|
| `product.variant` / `product.complete` | The detected product model, and whether the sensor set is complete (`P1` / `true`) |
| `effective_rate_hz`, `right.effective_rate_hz` | Actual frame rate of the left and right hands (both `200.0`). Top-level fields such as `capture_gate` and `mapper_quality` belong to the left hand; the right hand's fields of the same name are under `right` |
| `capture_gate.open` | Whether the timestamp gate is open; data is output only when it is `true` (`true`). It is normal for it to be closed for a few tens of milliseconds right after startup |
| `mapper_quality.stamp_trust` | Timestamp trust level (`trusted`): `trusted` is normal; `coasting` means slightly lower accuracy that is still within the allowed range, and data is output as usual; `untrusted` means the timestamps cannot be trusted and the timestamp gate closes as a result; for the causes see N2104 in section 3 of *07 Logging and Error Codes* |
| `stream_counters.frames_dropped_local` / `seq_gap_frames` | Number of frames dropped on the host side / missing on the glove side (both `0`) |
| `pairing.strict_sync_lost` | Whether bimanual hardware synchronization has been lost (`false`) |
| `pairing.device_skew_degraded`, `skew_alarms.count` | Whether bimanual sampling alignment exceeds its budget (`false`); the number of sampling-alignment notices (N2205 / N2206) received since the node started (`0`), with the latest 8 in `skew_alarms.recent`, each carrying `wall_ns` and `msg`. For what each statistic means, see section 5 of *09 Timestamp Synchronization* |
| `node.pairs_published` | Number of bimanual joint-angle messages the node has published |

`/revohuman/pair/tracker_status` (Trackers and base stations):

| Field | Meaning |
|---|---|
| `running` / `dead_reason` | Whether Tracker capture is running (`true`); when it has stopped, `dead_reason` gives the reason |
| `trackers.<serial>.healthy` / `pose_rate_hz` | Whether each Tracker is healthy, and its pose rate (`true` / about `249.8`) |
| `session.roles.left.online` / `session.roles.right.online` | Whether the left / right Tracker is online (`true`) |
| `session.reference.ready` | Whether a zero pose exists (see section 4) |
| `session.startup.restore.status` | Whether the saved zero pose was reused at startup (`ok`); if not, `detail` gives the reason (see section 4) |
| `session.geometry.ok` | Whether the base station geometry meets requirements (`true`); if not, `errors` / `flags` give the reason |
| `world.pose_watch` / `world.raw_watch` | Whether the base station movement detectors are working (`ok`); this does not mean the base stations have not moved. When movement is detected, `world.latched` is `true`; translation or horizontal rotation cannot be detected (section 8 of *03 Base Stations and Pairing*) |
| `lighthouses.declared` | Declared base stations (those entered as described in *03 Base Stations and Pairing*) |

## 4. Tracker zero pose

`tracker_delta_left|right` is the Tracker's pose increment relative to the **zero pose**. At startup the node reuses the zero pose last saved to disk
(the same one that the recording scripts of *04 Recording* use); if there is no zero pose to reuse, these two topics publish no data.

The increment is expressed in the Tracker's own frame at the moment the zero pose was recorded (`frame_id` is `revohuman_<hand>_tracker_zero`), and does not depend on the origin or orientation of the base station frame.

A saved zero pose is reused only if all three of the following hold:

- it was recorded no more than 8 hours ago;
- the base stations have not been recalibrated or replaced since then (the zero pose carries a fingerprint of the base station geometry);
- the left and right hands still use the same two Trackers as when the zero pose was recorded.

Otherwise the node logs a line `落盘零位不沿用（<原因>）：…` (saved zero pose not reused (reason): …),
`tracker_delta_*` publishes no data, and you need to call `tracker/set_reference` again. Whether the zero pose was reused can also be seen in
`session.startup.restore.status` in `tracker_status` (`ok` means reused).

To record the zero pose again, put both hands in the zero-pose posture, hold them still, and then call:

```bash
ros2 service call /revohuman/pair/tracker/set_reference std_srvs/srv/Trigger
```

Example output:

```text
requester: making request: std_srvs.srv.Trigger_Request()

response:
std_srvs.srv.Trigger_Response(success=True, message='{"calibration_id": "ac92e87ed83449228d45546c8af53750", "baseline_m": null, "note": "单站：间距基线不适用", "path": "/home/<用户名>/.local/state/revohuman/tracker/calibration.json"}')
```

With only one base station, `baseline_m` is `null` and `note` is `单站：间距基线不适用` (single station: spacing baseline not applicable), which is normal; with two base stations, `baseline_m` is the distance between the two base stations (meters).

`success=True` means the zero pose has been recorded and saved to disk; the next time the node starts, it is reused according to the three conditions above. Then confirm that the increment topics are being published:

```bash
ros2 topic hz /revohuman/pair/tracker_delta_left
```

If the base station geometry does not meet requirements, zero-pose calibration is rejected (`success=False`, with the reason given in `message`); handle it as described in *03 Base Stations and Pairing*.

## 5. Glove services

Read the glove serial number and run the read-only self-test:

```bash
ros2 service call /revohuman/pair/left/get_sn std_srvs/srv/Trigger
ros2 service call /revohuman/pair/left/selftest std_srvs/srv/Trigger
```

Example output:

```text
requester: making request: std_srvs.srv.Trigger_Request()

response:
std_srvs.srv.Trigger_Response(success=True, message='<序列号>')

requester: making request: std_srvs.srv.Trigger_Request()

response:
std_srvs.srv.Trigger_Response(success=True, message='ok')
```

`get_sn` returns the serial number stored in the glove firmware, or an empty string if none is stored (still with `success=True`); `selftest` returns `ok` when it passes.
Do not tell the left and right hands apart by the characters of the serial number: the SDK first uses the handedness stored in the glove firmware and only falls back to the serial number when none is stored; see section 2.1 of the *RevoHuman SDK Reference Manual*.

During the self-test that hand stops publishing data for about 50 ms, so **do not call it while recording**. For the right hand, replace `left` with `right`.

For the other glove services, see section 9.2. Of these, `tactile_tare` (tactile tare) works only on product models with tactile sensing; called on P1 it returns `success=False`,
with a `message` that starts with `E1805`.

## 6. Recording with rosbag

Record all RevoHuman topics, and press `Ctrl+C` once you have recorded enough:

```bash
mkdir -p ~/revohuman_bags && cd ~/revohuman_bags
ros2 bag record -o demo -e '/revohuman/pair/.*'
```

Inspect what was recorded:

```bash
ros2 bag info ~/revohuman_bags/demo
```

Example output (about 15 seconds recorded):

```text
Files:             demo_0.db3
Bag size:          7.0 MiB
Storage id:        sqlite3
Duration:          14.870316709s
Start:             Sep 27 2026 23:49:44.274683357 (1790552984.274683357)
End:               Sep 27 2026 23:49:59.145000066 (1790552999.145000066)
Messages:          17874
Topic information: Topic: /revohuman/pair/joint_states | Type: sensor_msgs/msg/JointState | Count: 2974 | Serialization Format: cdr
                   Topic: /revohuman/pair/status | Type: std_msgs/msg/String | Count: 15 | Serialization Format: cdr
                   Topic: /revohuman/pair/tactile_tare_state | Type: std_msgs/msg/String | Count: 1 | Serialization Format: cdr
                   Topic: /revohuman/pair/tracker_delta_left | Type: geometry_msgs/msg/PoseStamped | Count: 3717 | Serialization Format: cdr
                   Topic: /revohuman/pair/tracker_delta_right | Type: geometry_msgs/msg/PoseStamped | Count: 3717 | Serialization Format: cdr
                   Topic: /revohuman/pair/tracker_pose_left | Type: geometry_msgs/msg/PoseStamped | Count: 3717 | Serialization Format: cdr
                   Topic: /revohuman/pair/tracker_pose_right | Type: geometry_msgs/msg/PoseStamped | Count: 3717 | Serialization Format: cdr
                   Topic: /revohuman/pair/tracker_status | Type: std_msgs/msg/String | Count: 16 | Serialization Format: cdr
```

How to check: `Count` divided by `Duration` should be close to each topic's rate. Here the joint angles give 2974 / 14.87 s ≈ 200 Hz and the Tracker 3717 / 14.87 s ≈ 250 Hz;
`status` and `tracker_status` publish one message per second, and `tactile_tare_state` is published only on change (one message at startup). Reserve about 1.7 GB of disk space per hour (scaled from 7.0 MiB / 15 s in this example).

- If the directory given by `-o` already exists, `ros2 bag record` exits with an error; just use another name.
- The time stored with each message in the bag is the **arrival time**; for alignment across topics, use `header.stamp` in the message (the sampling time); for how to align, see section 3 of *09 Timestamp Synchronization*.
- If you need metadata such as synchronization health and the zero pose, use the SDK recording of *04 Recording* (MCAP format).

## 7. Single-hand mode

Use single-hand mode when only one glove is connected. First press `Ctrl+C` in terminal 1 to stop the bimanual node, then start:

```bash
ros2 launch revohuman_bringup revohuman.launch.py mode:=left
```

For the right hand, use `mode:=right`. Single-hand topics and services are under `/revohuman/left` (or `/revohuman/right`), and their names have no left/right suffix:

```bash
ros2 topic hz /revohuman/left/joint_states
```

The output ends roughly as follows, again at about 200 Hz:

```text
average rate: 199.996
	min: 0.001s max: 0.009s std dev: 0.00034s window: 2207
```

At startup the single-hand node reuses the zero pose recorded in bimanual mode (terminal 1 shows a line `沿用落盘零位 …` (reusing the saved zero pose …)), so there is no need to record it again; the conditions are the same as in section 4.
If terminal 1 shows `落盘零位不沿用（…）` (saved zero pose not reused), record the zero pose again on the single-hand node as described in section 4.

Do not start the bimanual and single-hand nodes at the same time: a glove can be opened by only one process.

## 8. Parameters

List all parameters supported by the launch file:

```bash
ros2 launch revohuman_bringup revohuman.launch.py --show-args
```

Parameters are given on the command line in the form `name:=value`, for example `mode:=left`. The command line takes precedence over the parameter file
`~/ros2_ws/src/revohuman_bringup/config/revohuman.yaml`, and the parameter file takes precedence over the node defaults.
Common parameters for P1:

| Parameter | Default | Description |
|---|---|---|
| `mode` | `pair` | `pair` for both hands; `left` / `right` for a single hand |
| `product` | `auto` | Product model, detected automatically; can also be set to `P1` |
| `rate_hz` | `200.0` | Glove publish rate (Hz) |
| `pair_mode` | `strict` | `strict`: output only bimanual pairs from the same hardware synchronization cycle; `best_effort`: allow pairs within 1 ms |
| `tracker_mode` | `required` | `required`: refuse to start if the Trackers cannot be started; `auto`: publish only glove data if the Trackers cannot be started (still refuses to start if it cannot find the serial number of that hand's Tracker); `off`: do not use the Trackers |
| `tracker_frame_id` | `world` | `frame_id` of `tracker_pose*` |
| `tracker_geometry_gate_mode` | `error` | Reject zero-pose calibration when the base station geometry does not meet requirements |
| `allow_calibration` | `false` | Whether to provide the glove encoder calibration services `calibrate` / `clear_calibration` (they write to the device; keep this off normally) |
| `button` | `false` | Bimanual mode: enable the glove button, publishing one `button_event` per press (section 9.1); if the firmware does not support it, capture continues as usual. Single-hand mode does not support the button |
| `log_level` | `info` | Node log level `debug` / `info` / `warn` / `error` |

## 9. Topics and services overview

### 9.1 Topics

| Both hands (`/revohuman/pair/`) | Single hand (`/revohuman/left/` or `/right/`) | Type | Description |
|---|---|---|---|
| `joint_states` | `joint_states` | `sensor_msgs/JointState` | 42 joints for both hands (21 left + 21 right) / 21 joints for a single hand, in radians |
| `tracker_pose_left` / `tracker_pose_right` | `tracker_pose` | `geometry_msgs/PoseStamped` | Absolute pose in the base station frame |
| `tracker_delta_left` / `tracker_delta_right` | `tracker_delta` | `geometry_msgs/PoseStamped` | Increment relative to the zero pose, with `frame_id` `revohuman_<hand>_tracker_zero`; published only when a zero pose exists |
| `status` | `status` | `std_msgs/String` | 1 Hz glove status JSON |
| `tracker_status` | `tracker_status` | `std_msgs/String` | 1 Hz Tracker status JSON |
| `tactile_tare_state` | `tactile_tare_state` | `std_msgs/String` | Tactile tare state JSON of the form `{"stamp_ns", "<hand>": {...}}`, with one entry per hand in bimanual mode; one message at startup, afterwards published only on change. On P1, `available` is `false` |
| `button_event` | — | `std_msgs/String` | Glove button event JSON, present only with `button:=true`; see below |

- Data topic QoS: BEST_EFFORT, depth 10.
- Status topic (`status`, `tracker_status`, `tactile_tare_state`) QoS: RELIABLE + TRANSIENT_LOCAL, depth 1; a subscriber with mismatched QoS receives nothing at all.
- `button_event` publishes one message per valid press, with the fields `hand`, `mode` (`start` / `end`, the glove-side state, for reference only), `press_sequence`,
  `press_count`, `missed_presses`, `recv_wall_ns`, `sample_wall_ns`, `seq`, `generation` and `event_id` (monotonically increasing within the node, for deduplication).
  Its QoS is RELIABLE + VOLATILE, depth 10: a subscriber that connects late does not receive earlier presses, so it does not take an old press as a fresh start / end.
  The node only forwards presses and does not control recording; if the firmware does not support the button, there are no events, and `button.<hand>.supported` in `status` is `false`.
- Every `header.stamp` is a sampling time.

### 9.2 Services

| Service (both hands: under `/revohuman/pair/left/` and `/revohuman/pair/right/`; single hand: under `/revohuman/<hand>/`) | Type | Description |
|---|---|---|
| `get_sn` | `std_srvs/srv/Trigger` | Read the serial number stored in the glove firmware; empty string if none is stored |
| `selftest` | `std_srvs/srv/Trigger` | Read-only self-test; that hand's stream stops for about 50 ms |
| `tactile_tare` | `std_srvs/srv/Trigger` | Tactile tare, the same as holding the glove button for about 2 seconds; does not touch the encoder calibration; always provided; blocks for about 3.5 s; on success `message` is the tare state JSON, on failure it starts with `E1805` |
| `calibrate` | `revohuman_msgs/srv/Calibrate` | Encoder calibration (writes to the device); provided only with `allow_calibration:=true` |
| `clear_calibration` | `std_srvs/srv/Trigger` | Clear the encoder calibration (writes to the device); provided only with `allow_calibration:=true` |

| Service (under `/revohuman/pair/` or `/revohuman/<hand>/`) | Type | Description |
|---|---|---|
| `tracker/set_reference` | `std_srvs/srv/Trigger` | Record the zero pose and save it to disk |
| `tracker/get_status` | `std_srvs/srv/Trigger` | Return the Tracker status JSON |
| `tracker/set_calibration_mode` | `std_srvs/srv/SetBool` | Enter base station calibration (do the base station calibration from the command line as described in *03 Base Stations and Pairing*) |

## 10. Node startup and restart

- At startup the node does **not** run the base station startup check, and does not record a zero pose automatically: it reuses the zero pose last saved to disk. To see whether the base stations meet requirements, look at
  `session.geometry` in `tracker_status`. When a base station is moved, the node logs an ERROR and stops the Tracker data (translation or horizontal rotation cannot be detected; see section 8 of *03 Base Stations and Pairing*);
  in that case, recalibrate the base stations as described in *03 Base Stations and Pairing* and then restart the node. The node performs fewer run-time checks than the SDK: whenever a base station has moved, recalibrate; do not wait for the node to report an error.
- When the node exits with exit code 5, it is switching Tracker mode (running ↔ base station calibration), and launch starts it again automatically;
  if it restarts more than 10 times within 60 seconds, it is not restarted again.

## 11. Common issues

| Symptom | Fix |
|---|---|
| `Package 'revohuman_bringup' not found` | The current terminal has not loaded the workspace: open a new terminal and try again, or run `source ~/ros2_ws/install/setup.bash` |
| `ros2 topic list` shows no `/revohuman/...` | The node has not started or has exited; check the log in terminal 1; `ROS_DOMAIN_ID` must be the same in both terminals |
| Terminal 1 reports `left 手的手套不在位` (the left hand's glove is not present) (or right) | This glove is not connected properly; check it as described in section 3 of *02 Hardware Connection*; if only one glove is connected, use single-hand mode (section 7) |
| Terminal 1 reports that the glove serial port is in use | `revohuman-live`, a recording script or another ROS node is using the glove; close it first |
| Terminal 1 reports `腕部相机启动失败` (wrist camera failed to start) and exits | PTV1 requires the wrist camera by default (leaving `camera_mode` empty means `required`): check that the glove unit with the camera is connected properly and that the current user can read and write `/dev/video*` (in a container `run.sh` grants this; see section 6 of *08 Running in Containers*); to look at the glove data only for now, add `camera_mode:=off` |
| Terminal 1 reports `tracker 启动失败` (tracker failed to start) and exits | The Trackers are not connected properly or the base stations are not set up: check as described in *03 Base Stations and Pairing*; to look at the glove data only for now, add `tracker_mode:=auto` |
| Terminal 1 reports `需要 tracker_left_serial，但找不到` (tracker_left_serial is required but was not found) (or right) | The node cannot tell which Tracker this hand uses: give the serial number using one of the methods listed in the error, for example `tracker_left_serial:=LHR-xxxxxxxx`; to look at the glove data only for now, add `tracker_mode:=off` (`auto` also refuses to start in this case) |
| `ros2 topic echo` prints nothing for a status topic | `--qos-reliability reliable --qos-durability transient_local` was not given |
| `tracker_delta_*` has no data (`ros2 topic hz` prints nothing) | There is no zero pose to reuse (if the node log has `落盘零位不沿用（…）`, the reason is given there): call `tracker/set_reference` (section 4) |
| `set_reference` returns `success=False` | Check the reason in `message`; if the base station geometry does not meet requirements, recalibrate as described in *03 Base Stations and Pairing* |
